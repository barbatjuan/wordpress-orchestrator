# House-rules checklist (the gate for the orchestrator's defaults)

Verifies the orchestrator's "House rules" (`agents/wordpress-orchestrator.md`). Run every row. Report
PASS / FAIL / UNVERIFIED per row — never blank.

Checks run server-side (`SKILL.md` Hard Rules): fetch the compiled CSS / front HTML and count
selectors and strings, or read WordPress options directly. Rows marked **eyes** cannot be proven that
way — ask the user and say so; never claim a visual result you did not see. Rows marked **measured**
read real geometry in the in-app browser and are provable neither from CSS nor server-side: where the
browser cannot reach the host they are UNVERIFIED, never PASS.

Run every per-page row on EVERY page in scope, not just the home.

| 11 | Fewest containers that do the job, and no setting on the wrong element type | No container nested "just because": none empty, none wrapping a single widget without carrying its own background/border/shadow, changing direction at a breakpoint or boxing that widget where no ancestor already does (padding alone never earns a container), no section whose only child is a flex row (the section IS the row), no photo living as a container `background_image`, nothing past depth 3, no widget carrying container-only keys and no container carrying the underscore forms | `require_once` the sandbox's `es-builder.php` and **call `es_container_audit()`** on the `json_decode`d `_elementor_data` of each page AND each Theme Builder template in scope. | 17 | No live orphans, and old URLs go somewhere | A slug that moved leaves no second page competing for it, and its old URL redirects instead of 404ing | Read the `es_slug_redirects` option — `{old_slug: new_slug}`, written by `es_migrate_slug()`. Worlds: the rename is W1 or W3 (library call); the redirect is proven in W2 by requesting the old path and requiring a 301. | 18 | A form that does not deliver is not a form | One real submission ARRIVES, and the recipient is an address the client can read | Two things. | 22 | The sandbox is empty at hand-off | `wp-content/novamira-sandbox/` holds nothing after delivery | Call `es_sandbox_report()` and require an EMPTY list. ## The three worlds a row can be checked in

**Only the local-then-copy route needs this section.** Building DIRECTLY on the client's WordPress
through the connector (the default, and the only route for an existing site) gives one site
with full PHP execution, so every row runs in one place. Read the rest only when the site was built
locally and copied to a production that has no connector. There, naming the world matters: a row that
reads as checkable everywhere and is checkable nowhere is how UNVERIFIED quietly becomes PASS.

- **W1 — local, before the transfer.** Full PHP, full browser, no connector needed. **The most
  capable of the three**, and where the whole pass runs.
- **W2 — production over HTTP.** Roughly half these rows run unchanged against any reachable URL.
- **W3 — production by ephemeral PHP.** `wp eval-file - < es-builder.php` runs the library against
  production **writing nothing to disk**. The question is not "is there SSH?" but *can one PHP file
  be evaluated against production's WordPress leaving nothing behind* — SSH with wp-cli yes, a
  cPanel terminal yes, phpMyAdmin alone no.

**Rows compose across worlds, and the composition is the row.** Row 16: layer (a) is options, proven
in W1; layer (b) is the served HTML, proven in W2; neither alone is the row. The delivery gate reads
that composition and never one world by itself.

**Without a W3 arm, rows 11 and 31(a) have no production arm at all.** They read stored data, and
no HTTP request can see it. The local pass carries them (the migration plugin copying the site
faithfully is an assumption, stated as one, not a check). Report UNVERIFIED for production and say
which rows: **UNVERIFIED is still not a pass**, and no fourth verdict exists.

## Honest limits — do not dress these up

- **Rows that depend on WooCommerce** (1, 2) do not apply to a build without WooCommerce — mark them
  N/A, not PASS.
- **Rows 13–15 need headless Chrome to REACH the URL.** Whether it reaches a NovaMira sandbox host is
  UNVERIFIED (the in-app browser is usually policy-blocked there; headless Chrome is a different path
  not yet tried). If it cannot connect, the script prints `UNREACHABLE` and runs nothing: report that
  as a tooling gap, never as a failing audit or a score of zero.
- **`UNREACHABLE` is flaky on Windows — re-run before believing it.** The same public URL alternates
  between a clean run and `EPERM, Permission denied: …\Temp\lighthouse.<n>` (antivirus holding the
  temp profile is the likely cause). The script uses a unique Chrome profile per attempt and retries
  three times with a backoff, which reduces it but does not eliminate it. Never report a site as
  unreachable off a single failed run.
- **Row 31 covers four axes of five, and two of them only halfway.** Scale and elevation are proven
  twice (declared and rendered); ground and density once, at the declaration; composition not at all
  (named to the user and left to their eyes). Never imply five axes tested.
- **A Lighthouse score is not a visual sign-off.** 100/100 on a page that looks broken is still a
  broken page; these rows add a floor and do not replace the user's eyes.
- **The performance number is NOISY — treat one run as an estimate.** Five runs against the SAME url
  on the same machine scored 95, 74, 71, 69 and 97 (LCP 2.5–5.0 s). Never report a performance delta
  from single runs on different machines or networks; take the best of three on the same machine, and
  say so. Accessibility, best-practices and SEO inspect the DOM instead of timing it, which is why
  they are the ones that block.
